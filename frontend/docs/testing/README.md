# Ручные тест-кейсы фронтенда (UI)

Набор ручных проверок веб-интерфейса «Абсолют 555» (React SPA). Кейсы описывают
поведение, которое реально есть в `frontend/src/` и закреплено браузерными тестами в
`frontend/e2e/specs/`. Выполняются в браузере без чтения исходного кода. Проверки HTTP
API — в `backend/docs/testing/README.md`.

## 1. Окружение

### Вариант А — полный стек (основной)

```bash
cp infra/.env.example infra/.env
docker compose -f infra/docker-compose.yml --env-file infra/.env up -d --build
```

Фронтенд отдаёт nginx: `http://localhost:3000` (`FRONTEND_HOST_PORT=3000` в
`infra/.env.example`; если порт в `.env` изменён — подставьте свой). nginx проксирует
`/api/` на `backend`, поэтому данные настоящие.

### Вариант Б — dev-сервер Vite (в каталоге `frontend/`)

| Команда | Что даёт | Когда |
|---|---|---|
| `npm run dev` | Vite с прокси на бэкенд; требует `VITE_API_PROXY_TARGET` в `frontend/.env` | правка UI при поднятом бэкенде |
| `npm run dev:mock` | режим `--mode mock`: запросы перехватываются в браузере фикстурами `src/dev/`, бэкенд не нужен | проверка вёрстки и навигации без данных сервера |

Адрес dev-сервера печатает Vite при старте (`Local: http://localhost:<порт>`). Во всех
кейсах `<BASE>` — корень фронтенда: `http://localhost:3000` или адрес Vite.
Путь в шаге (`/feed`) означает `<BASE>/feed`; `<FRONT_URL>` в кейсах — то же, что `<BASE>`.
`<LISTING_ID>`, `<SELLER_ID>`, `<SUPPLIER_ID>` — идентификатор из адресной строки после
перехода на карточку, профиль или витрину (последний сегмент пути).

Браузер: актуальный Chrome или Firefox. Ширина окна «десктоп» — от 1280 px, «телефон» —
390 px (DevTools → Device toolbar). Нижняя панель вкладок видна только на телефонной ширине.

## 2. Учётные записи

### Как интерфейс входит

Кнопки «Войти» (шапка) и «Попробовать снова» (экран колбэка) уводят страницу на
`/api/v1/auth/oauth/yandex/start` — вход в UI **только через Яндекс ID**
(`src/shared/session/signIn.ts`). После Яндекса браузер возвращается на
`/auth/callback?code=…`, код меняется на токены, открывается `/feed`.
Гостевого входа в интерфейсе нет. Сессия хранится в `localStorage` браузера под ключом
`absolute.session`.

### Полный стек без ключей Яндекса

1. Получите токены нужной записи гостевым входом, как в `backend/docs/testing/README.md` §2
   (`POST /auth/guest/login` с `device_id` из таблицы ниже).
2. Назначьте роль через `psql` тем же `UPDATE users SET role = '<роль>', is_guest = false`
   (для `GUEST_G` роль не меняйте).
3. Откройте `<BASE>`, DevTools → Console, выполните (подставив значения):

```js
localStorage.setItem('absolute.session', JSON.stringify({accessToken: '<access_token>',
  refreshToken: '<refresh_token>', userId: '<user_id>', role: '<роль>',
  displayName: 'QA', avatarUrl: null}))
```

4. Обновите страницу. Выход из записи — `localStorage.removeItem('absolute.session')` и
   обновление страницы (или «Выйти» в профиле).

С ключами Яндекса — обычный вход кнопкой «Войти» разными Яндекс-аккаунтами, роль
назначается так же через `psql`, затем повторный вход.

### Именованные учётные записи

| Имя в кейсах | `device_id` | Роль | Кто это в UI |
|---|---|---|---|
| `SELLER_A` | `qa-seller-a` | `user` | продавец |
| `BUYER_B` | `qa-buyer-b` | `user` | покупатель |
| `GUEST_G` | — | нет сессии | незалогиненный посетитель: `absolute.session` удалён |
| `MODERATOR_M` | `qa-moderator-m` | `manager` | модератор, видит «Модерация» |
| `ADMIN_X` | `qa-admin-x` | `admin` | администратор, консоль людей |
| `IMPORTER_I` | `qa-importer-i` | `importer` | поставщик под привоз |

Для UI «гость» — это отсутствие сессии, а не гостевой токен: интерфейс считает вошедшим
любого, у кого сохранена сессия.

### Режим `dev:mock`

`src/dev/mockServer.ts` при загрузке сам заводит демо-сессию: роль `admin`, имя «Михаил»,
`userId` = `u1` — поэтому открываются личные разделы и модерация. Гость — добавьте
`?guest=1` к любому адресу (выбор запоминается в `localStorage`, ключ
`absolute.mock.guest`); вернуть сессию — `?guest=0`. Других ролей режим не даёт: кейсы,
которым нужны `SELLER_A`/`BUYER_B`/`MODERATOR_M`/`IMPORTER_I` как разные люди, выполняйте
на полном стеке. Mock не проверяет права — отказы сервера в нём не воспроизводятся.

## 3. Шаблон кейса и легенда

| Поле | Смысл |
|---|---|
| **ID** | `TC-<ОБЛАСТЬ>-NNN`, уникален во всём наборе |
| **Название** | какой результат проверяется |
| **История** | `NN — <название из ProductSpecification/stories.md>` или `базовая функциональность` |
| **Описание** | зачем кейс существует, какое требование он защищает |
| **Приоритет** | High — основной сценарий или безопасность; Medium — важное правило; Low — граничный случай |
| **Предусловия** | окружение, учётная запись, состояние данных до шага 1 |
| **Тестовые данные** | точные значения для ввода, адреса, файлы |
| **Шаги** | нумерованные; один шаг — одно действие в браузере: открыть адрес, нажать кнопку с точной надписью, ввести точное значение |
| **Ожидаемый результат** | точный видимый текст, элемент или адрес в строке браузера |
| **Статус** | `Not run` / `Pass` / `Fail` / `Blocked` |
| **Фактический результат** | заполняет исполнитель |

Статусы:

- **Not run** — кейс ещё не выполнялся (исходное значение).
- **Pass** — фактический результат совпал с ожидаемым полностью.
- **Fail** — хотя бы одно расхождение; опишите его и приложите скриншот.
- **Blocked** — выполнить нельзя (стек не поднят, нет ключей Яндекса, не выполнено
  предусловие); укажите причину.

Надписи в кейсах взяты из исходников дословно, включая «ё» и кавычки. Расхождение в одной
букве — Fail.
