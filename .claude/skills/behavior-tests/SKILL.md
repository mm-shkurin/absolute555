# Поведение → сценарий → тест → правка → доказательство

BDD (Behavior Driven Development) вырос из TDD: TDD проверяет модуль кодом для
разработчика, BDD описывает **поведение системы глазами пользователя** языком, понятным
всей команде, и делает это описание исполняемым тестом.

Выведено из сессии, где набор был зелёным, а у человека не работали чат, отклик, фото,
черновики и карта замеров. Тесты проверяли слой, а ломалось на стыке слоёв; сценарии
Gherkin лежали в спеках (`ProductSpecification/stories/*/tests/*.md`), а в исполняемых
тестах их не было — спецификация и тест разошлись молча.

## Режим цикла по покрытию

`/behavior-tests --front 90%` или `--back 90%` — навык крутится итерациями по одной
стороне до цели: замер → область → сценарии → тест → правка → коммит, с журналом и
таблицей в `ProductSpecification/coverage/<сторона>/`. Механика, формат журнала,
остановка и итоговая сводка — `loop.md` рядом с этим файлом. Без флагов навык работает
по одному поведению, как описано ниже.

## 0. Аудит имеющегося — всегда первым

Прежде чем писать новый сценарий, проверить, что уже есть в области (репо, сторона или
экран, который трогаем):

- сценарии Gherkin из спек (`stories/*/tests/*.md` и `stories/done/*/tests/*.md`) против
  исполняемых тестов: какие есть дословно, какие только пересказаны, каких нет;
- тесты, которые проверяют слой, а не шов (таблица в шаге 3), и слабые проверки
  (`is not None`, `toBeTruthy`) вместо строгих;
- выключенные тесты (`skip`) — это не отгруженное поведение.

Результат — список пробелов по областям с приоритетом. Его разбирают вместе с
пользователем, и только после этого начинается BDD-цикл (шаги 1–5) по пунктам списка.
Без аудита новый сценарий легко дублирует имеющийся или пропускает сломанный шов рядом.

## 1. Discovery — сначала поведение, а не код

Сформулировать правило на **конкретных примерах** из слов пользователя: кто, что сделал,
что должен увидеть. Жалоба «ничего не происходит» — это уже пример, а не диагноз.

Для бага — найти, до какого звена дошёл запрос, **по фактам**, прежде чем читать код.
Путь: браузер → бандл → nginx → роутер → сервис → БД/хранилище → ответ → экран.

- логи бэкенда — был ли запрос вообще (нет `PUT …/response` → рвётся на фронте);
- БД — что реально сохранилось (данные целы → врёт экран);
- `curl` по адресу из ответа (`minio:9000` → браузер не откроет);
- `grep` новой строки в бандле контейнера (сборка могла упасть молча).

Записать одну строку: «рвётся на звене X».

## 2. Formulation — сценарий Gherkin

```gherkin
Feature: Отклик поставщика на заявку
  Как поставщик, я хочу ответить ценой и сроком, чтобы начать разговор с покупателем

  Background:
    Given покупатель открыл заявку «Lexus GS»

  Scenario: Отклик открывает переписку с первой строкой
    When поставщик откликается ценой 1 900 000 ₽ и сроком 40 дней
    Then у обоих появляется переписка
    And первая строка — «Отклик на заявку: 1 900 000 ₽, доставка 40 дней»

  Scenario Outline: Цена принимается в том виде, в каком её пишут
    When поставщик вводит цену "<ввод>"
    Then сохраняется <число>
    Examples:
      | ввод      | число   |
      | 6 690 000 | 6690000 |
      | 6690000   | 6690000 |
```

- `Given` — исходное состояние, `When` — **одно** действие, `Then` — наблюдаемый снаружи
  результат, `And/But` — продолжение шага, `Background` — общие предусловия,
  `Scenario Outline` + `Examples` — одно правило на таблицу данных.
- Один сценарий — одно поведение. Конкретные данные вместо абстракций.
- В сценарии нет логики, нет названий классов, эндпоинтов и CSS — только то, что видит
  человек. Такой сценарий переживает рефакторинг и не хрупкий.
- Обязательно негативные ветки: отказ, пусто, недоступный внешний сервис, чужой объект.
- Сценарии, которые почти всегда упускают: «ушёл и вернулся», «ввёл как в подсказке»,
  «вторая сторона видит без перезагрузки», «после одобрения видно на публичной странице».

Сценарий кладётся в спеку истории **и** в сам тест (докстринг / имя `it`), дословно:
тест — исполняемая копия спеки, а не пересказ.

## 3. Automation — тест на шов, где ломается

Уровень теста выбирается по звену из шага 1, а не по удобству:

| Шов | Что ломалось | Тест |
|---|---|---|
| прокси | WebSocket без `Upgrade` в nginx | рукопожатие `curl` через `localhost`, не на порт бэкенда |
| формат провода | фронт читал `{type,message}` как `message` | разбор кадра на **реальной** форме ответа сервера |
| обёртка ошибки | код отказа лежал в `cause` | перевод отказа на объекте, который отдаёт `send` |
| таблица соответствий | роль `importer` не мапилась | тест на **каждое** значение перечисления сервера |
| ввод человека | «6 690 000», «97.3», неразрывный пробел | тест на то, что показано в плейсхолдере и на приборе |
| адрес для браузера | внутренний хост хранилища | база URL совпадает с заведомо рабочим (аватаркой) |
| состояние при возврате | новый черновик вместо старого | «открыл → ушёл → вернулся» |
| сборка | `tsc --noEmit` по корню ничего не проверял | та же команда, что в Dockerfile |

### Бэкенд (pytest, HTTP чёрным ящиком)

```python
def test_should_open_a_dialog_with_the_response_as_its_first_line(client, buyer, importer):
    """Scenario: Отклик открывает переписку с первой строкой
    Given покупатель открыл заявку
    When поставщик откликается ценой 1 900 000 ₽ и сроком 40 дней
    Then у обоих появляется переписка, первая строка — отклик
    """
    # Given
    request_id = ask(client, buyer).json()["request_id"]
    # When
    answered = respond(client, importer, request_id, price=1900000.0, delivery_days=40)
    # Then
    first = messages(client, buyer, answered.json()["dialog_id"])[0]
    assert first["kind"] == "system"
    assert "40 дней" in first["text"]
```

- Через HTTP, как клиент; строгие проверки полей (`==`), а не `is not None`.
- Внешние сервисы (GigaChat, S3-провайдер) подменяются автофикстурой в `conftest.py`.
- Запуск: `bash scripts/ci-local.sh --fast tests/<файл>.py`, затем без аргументов.

### Фронтенд

- **Логика** (vitest, чистые функции `logic/`): `it('<Then словами пользователя>')`,
  тело разбито на Given/When/Then. Сюда уходит всё правило — маппинг провода, разбор
  ввода, выбор шага, — компонент остаётся тонким.
- **Провод**: тест маппинга на объекте ровно той формы, что отдаёт сервер (копия
  ответа), включая `null`, вложенный `cause`, новые поля.
- **Браузер** (Selenium/e2e) — для сценариев, где поведение живёт только на экране:
  переход, кнопка появилась, вторая вкладка обновилась.
- Запуск: `npx tsc -b` (как в Dockerfile), `npx vitest run`.

## 4. Цикл правки

1. Сценарий записан. Тест написан и **красный по той же причине**, что у пользователя.
2. Минимальная правка **в слое причины**, а не симптома (фото не видно → адрес на
   сервере, а не CSS).
3. Одно правило — одна функция: список и мастер не считают шаги двумя копиями.
4. Тест зелёный → соседние наборы → полный набор стороны.
5. Смена смысла поля ломает старое правило: форма всегда шлёт число → «прислано ⇒
   ввёл продавец» ложно. Тест пишется на смысл, а не на форму запроса.
6. Вероятностный компонент (распознавание) без 100% точности: результат —
   подсказка с подтверждением человека; качество меряется отдельно на размеченном
   корпусе (`scripts/gauge_eval.py`: 0/50 → 47/50) и цитируется, а не утверждается.

### Когда падает тест после правки

- **Свой сценарий, поведение изменено намеренно** — переписать ожидание, указать в коммите.
- **Чужой сценарий, намерения не было** — это регресс, чинить код, не тест.
- **Нестабильный (гонка)** — прогнать отдельно и на чистом дереве прежде, чем связывать с правкой.
- **Фикстуры и тестовые данные** — часть контракта: новое обязательное поле провода
  правится в них в том же коммите, иначе падает сборка образа, а не тесты.
- Лимит 200 строк касается и тестов: переполненный файл → новый файл по сценариям
  одной функции, фикстуры импортом.

## 5. Доказательство перед «готово»

Каждый пункт — с цитатой вывода команды. Не выполнен — так и написать.

- [ ] сценарий есть в спеке и дословно в тесте;
- [ ] тест был красным и стал зелёным;
- [ ] полный набор стороны зелёный (бэкенд `ci-local.sh --fast`; фронт `tsc -b` + `vitest run`);
- [ ] сборка образа: код выхода 0 **и** нет `error` в логе, а не «последние строки без ошибки»;
- [ ] контейнер пересоздан, новая строка есть в отдаваемом бандле;
- [ ] живой запрос через тот же вход, что у человека (`localhost`), даёт ожидаемое;
- [ ] в коммите только свои файлы (`git show --stat`: дерево делят две сессии).
