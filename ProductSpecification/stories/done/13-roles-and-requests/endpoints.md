# Роли и заявки: manager, importer - API Endpoints

Новых маршрутов история не заводит: поток заявок уже смонтирован. Меняются правила на
существующих, и это единственное, что фронту надо перечитать.

| Method | Path | Что меняется |
|--------|------|--------------|
| POST | /api/v1/role/role-request | Гостю отказ; роль, которая уже есть, не запрашивается; `importer` в списке ролей |
| GET | /api/v1/role/my-role-requests | Без изменений |
| GET | /api/v1/role/role-requests | Без изменений |
| PUT | /api/v1/role/role-requests/{request_id} | Отказ требует комментария; решённая заявка не перерешивается; `manager` не выдаёт `manager` и `admin` |
| PUT | /api/v1/role/users/{user_id}/role | Без изменений: снятие роли, объявления остаются |

## Notes

- **`importer` — пятая роль.** Значение `importer` в перечислении ролей везде, где оно
  встречается: запрос роли, фильтр списка пользователей, прямая смена роли.
- **Гость получает `403`**, а не `401`: он вошёл, просто ему это не положено.
- **Заявка на роль, которая уже есть, — `409`.** Не «успех, ничего не делаю»: экран
  показал бы человеку заявку, которая никогда не будет рассмотрена.
- **Вторая живая заявка на ту же роль — `409`.** Правило уже действует; здесь оно только
  получает свой код вместо общего.
- **Отказ без комментария — `422`.** Как у отклонения объявления: человеку нужно то, что
  можно исправить, а подать заново он вправе сразу.
- **Решённая заявка — `409`.** Одобрение выдаёт роль, и повторное одобрение выдаёт её
  ещё раз; перевод отказа в одобрение — то же самое, только позже и незаметнее.
- **`manager`, одобряющий заявку на `manager` или `admin`, получает `403`.** Ручка
  «рассмотреть заявку» иначе становится дорогой наверх: запросить `admin` может любой.
- **Одобрение и выдача роли — одна транзакция.** Иначе бывает одобренная заявка без
  выданной роли, и по выдаче ролей уже нельзя судить по журналу заявок.
